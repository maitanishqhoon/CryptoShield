# CryptoShield — Known Limitations & Prototype Boundaries

As an academic proof-of-concept, CryptoShield focuses on demonstrating verifiable defensive architectures, cryptographic integrity controls, and detection heuristics. It has distinct architectural boundaries that differentiate it from commercial enterprise security products:

---

## 1. Monitoring & Telemetry Boundaries
- **Filesystem Read Visibility:** The OS filesystem monitor uses Python's `watchdog` library (wrapping Windows ReadDirectoryChangesW), which reliably captures file creations, modifications, deletions, and moves, but **does not capture arbitrary file read operations** without active instrumentation. Active file reads are observed via `AccessMonitor` hooks in controlled test harnesses.
- **Process Attribution & Causation:** Standard OS filesystem events do not automatically carry the PID of the writing process. Correlation between filesystem activity and process tables is heuristic unless established through direct instrumentation or owned subprocess handles. In adherence to Invariant 4, unknown process attribution must remain `UNKNOWN`.
- **Heuristic Threat Scoring:** The 0–100 threat score generated by `ThreatScorer` is a rule-based heuristic indicator designed for threshold triggering, not a calibrated Bayesian probability of compromise.

---

## 2. Containment Boundaries
- **Application-Level Containment:** `LabWriteGate` enforces write restrictions at the application level via `.write_gate_state` files that controlled simulators inspect before writing. It is **not an OS kernel minifilter driver** and cannot prevent arbitrary external processes from writing to disk.
- **Process Termination Scope:** In accordance with Invariant 3, the `ProcessController` only terminates child processes registered in `ControlledProcessRegistry` whose executable path, creation time, and owned handle are verified. It does not possess, nor does it claim, arbitrary kernel-level process killing capabilities.

---

## 3. Cryptographic & Recovery Boundaries
- **AES-GCM Streaming Plaintext Leakage Window:** AES-256-GCM streaming decryption yields decrypted bytes before the final 16-byte authentication tag is reached. If an unauthenticated restore were written directly to destination paths, invalid or tampered plaintext could be exposed. CryptoShield mitigates this by requiring an isolated staging directory and verifying both the GCM tag and the SHA-256 digest before committing files.
- **Key Access & Passphrase Security:** Cryptographic key unwrap operations require the master private-key passphrase. In automated demonstration and test modes, passphrases must either be prompted interactively or passed via secure test fixtures; passphrases are never persisted in plaintext logs or config files.

---

## 4. Exfiltration & DLP Boundaries
- **Mock Network Sockets Only:** Data exfiltration monitoring and DLP policy enforcement are strictly evaluated against local loopback mock sockets (`127.0.0.1:<port>`). No network packets are ever transmitted across external interfaces or physical networks.
- **Staging Detection Scope:** Staging detection monitors directory creations, zip/archive creation, and high-velocity reads within the laboratory boundary. It does not monitor arbitrary host staging outside `runtime/`.
